# 360° 全景与选择性播报开发记录

更新：2026-09-22。本文件记录当前实现及实测限制，不代表赛事最终验收已经完成。

## 本次实现

- HTTP 输入新增 `projection=rectilinear|equirectangular` 和 `heading_deg=-180..180`，默认保持普通视角。网页可选择全景并用键盘调整正前方。改变格式、角度、输入、播放位置或模式会清空会话与语音。
- 已拼接 2:1 全景分成前、左、右、后、上、下六个 90° 透视画面，组成 1152×816 图像，一次模型请求。看牌只截取前向 768×768 画面。原始双鱼眼 INSV 不冒充已拼接全景。
- 模型最多请求六个观察，返回紧凑 JSON，代码补全类别和受控中文名称。全景模型只需返回整张六宫格的 `box`，程序根据框中心确定所属面，再换算面内坐标和球面方位；模型不负责输出方向。跨面大框、缺框或无法定位的观察省略，其余有效观察继续；全部无法定位则明确返回uncertain。相邻面同类别且中心角接近的观察合并。
- 代码综合类别、方向和粗略远近排序。一般前方优先，侧方、上方可获得第二个名额，近距离后方疑似接近优先级最高。先去重再选候选，首项被去重不会阻止其它目标。详情最多六项，每次语音最多两个障碍，设施或标牌一次一项。
- 后方接近要求同会话、同类别、同面、相近中心连续三次出现；框高连续增长至少 8%，总增长至少 25%，时间跨度 1～20 秒（相邻有效观察不超过10秒，容纳云端实际抽帧间隔），且粗估为近处。多人关联有歧义、框跳变、长时间断帧、暂停或换会话均不累积接近证据。输出“疑似靠近”，不输出速度、碰撞时间或米数。
- `urgent` 播报可打断 `high`；仍只有一个最新待播候选，开始前检查会话和图像时效。HTTP 全景不启用 WebSocket，以免在缺少分面提示的实时模型中误解方向。
- 修复 Edge 中视频尚未开始播放时，`readyState` 已就绪但 Canvas 首次采到黑帧的问题：仅首次按键采集先等待一个解码帧，再暂停；后续按键保留当前暂停位置。

## 远近的含义

没有深度传感器或真实测距。行人、自行车、车辆、摩托车、围挡、路障用标称高度和透视框高划分粗略近/中/远（公式内部阈值为 2.5/5 米），误差可能很大，只参与优先级。台阶、地面设施、标牌、尺寸未知物体保持未知。不能把整幅等距柱状全景套进针孔公式，也不能根据雨棚占画面大就推断雨棚很近。普通顶棚属于设施 `canopy`，与悬空树枝等 `overhead` 障碍分开。

后方框增大只是相对接近的视觉线索，相机运动、变焦、遮挡变化仍会影响判断；没有 IMU、自运动补偿或深度，因此不能宣称已经完成可靠防碰撞。使用全景必须固定相机朝向，并先设置正前方；不自动跟随用户身体转向。

## 真实视频测试

输入为仓库中的 `VID_20260922_171452_00_007.insv`，约160秒，两路3840×3840鱼眼视频。只解码选定帧送云，不上传整段原片。原片上的方向及距离不作为360°校准结果。随后用户补充了960×480、160.19秒的2:1全景MP4，已用于实际全景验证。明细位于本机忽略目录 `work/panorama-check/`，包含场景文字，未提交仓库。

| 测试 | 结果 | 解释 |
|---|---|---|
| 改造前，两路5秒抽帧 | 一次7.30秒成功、一次8秒超时 | 成功帧得到三个标牌；第一次只读首项，模拟两秒后首项被去重，其余项也没有播报 |
| 加大完整目标结构 | 两次均8秒超时 | 不能仅增加模型输出数量 |
| 紧凑结构、1920像素原片六帧 | 3/6结构有效，0/6在6秒内 | 该分辨率高于普通网页输入，用于压力对照 |
| 快速模型试验 | 4/6结构有效，3/6在6秒内 | 有非法标签/字段，未改动默认模型配置 |
| 默认模型、网页同规格960像素、5/7/9秒×双镜头 | 6/6结构有效，4.281～5.707秒 | 全部满足模型阶段6秒期限；包含1～2项播报及去重后其它目标获得候选的记录 |

补充：区分顶棚并调整上方优先级后的两路5秒帧复测均返回有效结构，耗时5.406秒和4.861秒。

这些是小样本的结构、延迟与播报链路检查，不是准确率。人工查看发现雨棚容易被模型误当作悬空障碍，拍摄者也可能被计入行人；已经去掉“上方大框即近处”的规则并区分顶棚标签，仍需新素材验收。没有把原始鱼眼图的分类结果算成校准后的360°识别成功。

## 性能与开源复用

直接使用 [py360convert](https://github.com/sunset1995/py360convert) 的 `e2p`，固定版本1.0.4。其透视采样网格采用有界 LRU 缓存，六个方向可在连续帧复用；附带 [MIT许可](licenses/py360convert-MIT.txt)。没有逐方向发送六个云端请求。本机1920×960合成图12次投影测试，首次221ms，后续中位100ms、最大110ms；合成纯色图的压缩成本偏低，不代表所有路线画面。

阅读了 [BlindNav源码](https://github.com/Anthonyiswhy/blind_navigation_aid/blob/main/raspberry_pi/yolo_realsense_navigation.py)，借鉴其方向分区、距离分档冷却、近距离侧方关注及运动跳变限制的设计。本项目未复制该仓库代码，也未引入其RealSense/YOLO运行时；它具有深度与自运动补偿，不能把它的精度、速度或防碰撞能力写成CityLens的结果。

## 运行与复测

```powershell
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
pnpm --dir frontend build
.\scripts\start.ps1
```

网页选择“路线视频回放”→上传已拼接2:1全景MP4→“360°全景”→校准正前方→勾选处理说明→开始。USB相机若输出普通画面应选择普通固定视角。Link 2不是360°全景相机，本次没有X4 Air实时SDK取流。

人工评测脚本（会调用已配置模型并产生API费用）：

```powershell
.\.venv\Scripts\python.exe -m pip install -r scripts/video-requirements.txt
.\.venv\Scripts\python.exe -m scripts.evaluate_video 路线全景.mp4 --projection equirectangular --times 5 7 9 --heading 0 --name panorama-validation
```

脚本默认不保存帧，只保存本机评测JSON；`--save-frames` 显式保存选帧供人工检查。原始INSV只能作普通鱼眼诊断，不能选择equirectangular，距离估计禁用。样例模型禁止作为真实评测运行。

## 后方人物部分出框的补充（2026-09-22）

真实后方人物常出现腿部超出透视面的情况。新增受限备用规则：高度不完整、但左右边界完整的person，用0.5米标称体宽粗估远近（`distance_basis=apparent_width`），连续变化也改用框宽。该假设会受姿态、衣服和框误差影响，不是实测体宽；左右也被截断时仍保持未知。高度/宽度估算切换时清空趋势，不将不同量纲连续比较。

72～77秒、180°方向的6次新模型请求中5次成功、1次结构错误；成功帧有后方近处人物，但多人关联、框变化与测量方式切换没有满足连续接近条件，未输出“疑似靠近”。不能因规则测试通过就把实际接近功能标记为验收完成。

该片段还暴露同方向近/中距人物导致“后方发现行人；后方发现行人”的重复。已按最终播报措辞合并候选并覆盖对应冷却键，保留不同方向或接近升级提示。用5份已保存的真实模型结果重放新规则，无重复措辞；这属于规则回放，不计为5次新的真实模型验收。


跨分面跟踪更新：同一 `label` 在相邻全景面之间若球面 yaw 差不超过35°、pitch差不超过30°，按球面角度关联；局部框在换面时可以跳变，但尺度变化仍受0.4～2.5倍约束。多人匹配有多个候选时不合并，避免把两个行人伪装成接近。后方判定覆盖yaw绝对值≥120°的后侧扇区，不要求目标始终停留在名为back的面。
