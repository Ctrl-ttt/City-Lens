## 一、他点名的「最难点」我们说不出来 —— 方向维度缺「上方」

他说：

> 「不能光看脚下，还要看**头顶上**，最起码两米范围以内……**低垂的树枝、招牌**这类东西」

而我们的方向词表只有三个水平方向：

```python
# backend/rules.py
DIRECTION = {'left': '左前方', 'front': '前方', 'right': '右前方', 'unknown': '画面中'}
```

**没有「上方」。** 就算模型看到低垂树枝，它也只能说「前方发现障碍」——用户会以为在前面地上。这是**表达能力的缺口**，不是识别能力的缺口。

### 改法（两个文件各一处）

| 文件 | 改动 |
|---|---|
| `backend/vision.py` | `SYSTEM_PROMPT` 里方向枚举 `left/front/right/unknown` → 增加 `above` |
| `backend/rules.py` | `DIRECTION` 增加 `'above': '上方'`（或「头顶」） |

### ⚠️ 但必须先测再改

加了标签只解决「能不能说」，不解决「看不看得见」。胸挂／杖眼是平视镜头，**垂直视场可能根本拍不到头顶两米**。

**测试方法（约半小时，纯手工）**：把 Link 2 按胸挂高度架好，正前方 2 米处放一个物体，从视线高度缓慢往上抬，记录它在哪个高度从画面里消失。

- 拍得到 → 加 `above`，这是一条**硬证据**
- 拍不到 → 这是必须**主动写进答辩的已知限制**，不要等评委问出来

## 二、「地图已解决的不做」—— 标签表审计

收尾三选一，他没有三选一，而是重构了问题：

> 「你手里如果有一个『有声的地图』，那么『周围有什么』这个大概就不用再播报了……那你可以**叠加在地图之上，说它没有的东西**。」

按这个尺子审我们当前的允许标签（来自 `backend/vision.py` 的 `SYSTEM_PROMPT`）：

| 标签 | 地图能给吗 | 建议 |
|---|---|---|
| `bicycle` 共享单车 | **不能**（临时停放） | **保留 —— 这是核心价值** |
| `bollard` 隔离桩 | 不能 | 保留 |
| `step` / `stairs` 台阶楼梯 | 不能 | 保留（`ORDER` 里已是最高优先级） |
| `obstacle` 其它障碍 | 不能 | 保留 |
| `barrier` 围挡 | 部分（长期施工地图有，临时的没有） | 保留但注意 |
| `elevator` 电梯 | 部分（仅室内地图） | **待决策** |
| `entrance` 入口 | 部分 | **待决策** |
| `crosswalk` 斑马线 | **能**（地图标准数据） | **冗余候选** |
| `bus_stop` 公交站 | **能** | **冗余候选** |

### 反面意见（重要，别急着删）

王老师的前提是「现在这几个地图应用都很发达」。但**地图 App 对视障用户的真实可用性是另一回事**——「地图里有斑马线数据」不等于「用户能顺利拿到这条信息」。他是从业者，不是重度地图用户。

**建议做法**：把 `crosswalk`、`bus_stop` 降级为「**只在没有其它事件时才播**」，而不是直接删标签。这样既响应了他的意见，也不会在未验证的情况下砍掉可能真有用的信息。改动落在 `backend/rules.py` 的 `ORDER`（目前它们默认是 2，可以显式标出）。

## 三、一个被漏掉的前置条件：不解决 HTTPS，「让他们体验」就做不到

这是他最强的那条意见——

> 「在研发的过程当中，还要不断地征求他们的意见，甚至**不断地让他们来体验**」

——但我们**物理上做不到**。

**原因**：`getUserMedia` 要求**安全上下文（secure context）**。`http://localhost` 被浏览器豁免，所以在开发机上一直能跑；但**手机通过局域网 IP 打开 `http://192.168.x.x:8000` 不被豁免**，浏览器会直接拒绝访问摄像头。

也就是说：**想让王老师、或任何一位视障朋友在自己手机上试一次，现在打不开。**

### 改法（两条都不难）

- 自签证书 + uvicorn `--ssl-keyfile/--ssl-certfile`，前端走 `https://`（手机需手动信任证书）
- 或用内网穿透工具给一个 https 域名（演示当天最快）

**建议优先级靠前**——因为它是「采集更多真实反馈」的**唯一前置条件**，而按王老师自己的标准，我们最大的短板正是样本太少。

## 四、他说的话里，有一条**支持**我们现有设计

他讲「给盲人讲电影」时有个细节值得注意——他讲的是**专业人士讲电影「弥补了」视障朋友的理解**，而且盲人朋友**认可**这件事。

这意味着：他反对的不是「替用户做选择」，而是「**没了解用户就替用户做选择**」。

我们的 pipeline 恰好就是在**做选择**：`backend/rules.py` 里排序（台阶优先）、去重、**最多只播 3 条**、每次只念 1 条。这不是「看到什么念什么」，是**筛选后的解读**。

**这一点可以直接进答辩素材**，而且有采访支撑：

> 我们没有做成「看到什么念什么」，而是做排序和限流——因为受访的从业者指出，对盲人来说关键不是信息量，是「给他专业的、他能接受的东西」。

## 五、优先级建议

| 优先级 | 动作 | 成本 | 归属 |
|---|---|---|---|
| 1 | 测垂直视场（能否看到头顶 2 米低垂障碍） | 约半小时，纯手工 | 需硬件 |
| 2 | 解决 HTTPS，让手机能打开 | 半天 | 需网络方案 |
| 3 | 加 `above` 方向（视第 1 条结果而定） | 两行 + 单测 | 可立即做 |
| 4 | 审 `crosswalk` / `bus_stop` 的播报门槛 | 一行 | 可立即做 |
| 5 | 实测胸挂抖动对 `label:direction` 稳定性的影响 | 约半小时 | 需硬件 |

第 5 条补充说明：形态那条意见（「挂身上会晃」）**前提被污染了**——他回应的是我们临场说的「360 全景挂身上」，不是我们真实的产品。但**抖动确实影响我们的去重键 `label:direction`**，也会影响「连续两帧确认」这类方案的可行性，所以值得实测，而不是直接接受或直接忽略。
